## Decided against

| Idea                                                                    | From     | Why not                                                                                                                                                                                                                                                                                    |
| ----------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The widget drawn into the site's own page (Shadow DOM, a web component) | Day 27   | The site's scripts could read what guests type and change what they see; its CSS still leaks into a shadow root through inherited properties; booking would need CORS. An iframe isolates both ways and keeps server actions same-origin. The cost (resizing over `postMessage`) is small. |
| Following the guest's device by default in the embed                    | Day 27   | Most sites don't follow the device. A dark calendar on a light page looks broken, and with a different `color-scheme` the browser paints an opaque box behind the frame. Light by default; `system` is an option for sites that do follow it.                                              |
| `X-Frame-Options: ALLOW-FROM` for the embed                             | Day 27   | Obsolete: modern browsers ignore it. `frame-ancestors` is the standard, and X-Frame-Options has no "everyone" value, so the embed simply doesn't send it.                                                                                                                                  |
| A `sandbox` on the embed's iframe                                       | Day 27   | Sandboxing protects a page from a frame it doesn't trust. The site already runs our script with full power; the frame needs scripts, same-origin requests and forms anyway, so a sandbox would add nothing but breakage.                                                                   |
| Dynamic Client Registration on by default                               | Day 21   | Anyone could create a client row with no login, and the spec now deprecates it. CIMD needs no row until a real assistant shows up. A switch (`MCP_ALLOW_DCR`) exists for a client that can't do CIMD, read-only.                                                                           |
| `legacy: "reject"` on the MCP endpoint                                  | Day 21   | Better Auth's README suggests it, but it refuses every assistant still speaking a 2025 protocol revision. The SDK's default serves both, statelessly.                                                                                                                                      |
| Guests' notes in `list_bookings`                                        | Day 21   | A tool result fills the assistant's context, and guests' words should leave MeetReady only when the host asks about that booking (`get_booking`).                                                                                                                                          |
| A "prepare, then confirm with a token" pair of tools                    | Day 22   | The model can call both steps itself, so it proves nothing about the person. | Booking outside the host's rules through an assistant                   | Day 22   | An assistant that can book outside your hours, notice or buffers is the riskier one. | The assistant books by itself                                           | Day 19   | A writing tool on a public, anonymous page is what prompt injection aims at, and the form already validates everything a booking needs. ## Known issues

- **`/booking/{made-up-token}` returns 200** with the not-found page and `noindex` (Day 12). Profile and booking
  pages got real 404s from Proxy; the manage page didn't, because its URL is private and never linked publicly.
- **Sun times use each timezone's main city** (Day 9). Someone in Chattogram sees Dhaka's sunrise, a few
  minutes off. Knowing the exact town would need a location permission, which isn't worth it for colours.
- **The hero's colours no longer slide between cities** (Day 9). Real skies are per-city gradients, and CSS can't
  animate between two gradients. The brackets still slide.
