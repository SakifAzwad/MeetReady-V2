## 1. The logo

- **The mark is the product's own drawing:** one day from night through dawn, day and dusk, with a white bracket
  for working hours. It's the band from the booking page, squeezed into a square. A logo that means something
  in the product is easier to defend than a random shape, and it needs no explanation once you've seen the band.
- **Iterations (screenshots at 16, 32 and 180px):**
  - A tall bracket read as a "0".
  - The white bracket disappeared on the light "day" colour.
  - A fix with a navy stroke under the white one darkened both sides.
  - The final version is a wide, short bracket (it's a time range) with a faint ring **outside only**, the
    same trick as the band.
- **In the app it's CSS, not inline SVG:** an SVG gradient needs an `id`. With two logos on a page (header and
  footer), both would share one id, and if the first one is ever hidden, the second loses its gradient.
  `icon.svg` is the same drawing for browser tabs.
- **Files by convention:**
  - `icon.svg` for modern browsers.
  - `favicon.ico` for the rest: an ICO container holding 16/32/48px PNGs, written by a small script.
  - `apple-icon.png` for home screens.
  - `opengraph-image.png` for link previews.
  - Next.js turns these into the right `<link>` and `<meta>` tags. `metadataBase` makes their URLs absolute,
    which link previews require.
- **The link preview is a static PNG,** rendered once from an HTML page with the real fonts. A dynamic
  `ImageResponse` would need the fonts as TTF/WOFF (our packages only ship WOFF2) and would run code for an
  image that never changes.

## 2. Landing page

Sections follow the questions a visitor asks, in order:

1. **What is it?** Headline plus the live two-band demo (Day 6). City buttons now **slide** the colours and the
   brackets to the new timezone instead of jumping: a CSS transition on the gradient strip and the bracket
   positions.
2. **What would my guests see?** The **real booking-page components** (facts panel, band, time list) on sample
   data, with times generated by the real `generateSlots` and two meetings already booked, so the gaps show.
   Visitors can pick a time and press Continue; it explains what the real page does next.
3. **How it works:** three numbered steps.
4. **Features, "Built for both sides of the invite":** what hosts get and what guests get, then a separately
   boxed **"Coming next"** list. That list is clearly labelled as not built yet; mixing planned features into
   the "built" list would be dishonest, and an interviewer would ask.
5. **Under the hood:** the engineering section from Day 6.
6. **Questions:** native `<details>` elements. They're keyboard and screen-reader accessible with no
   JavaScript, and a browser's find-in-page searches them.
7. **Closing call to action** on a navy panel.

**Header:**

- Sticky and translucent, with logo, section links, GitHub, Log in and Get started.
- On phones it becomes a **disclosure menu**: a button with `aria-expanded` and `aria-controls`; Escape closes
  it. It's not a modal dialog. It pushes content down instead of covering it, so there's no focus to trap.

**Footer:** product and project links, including the day-by-day build notes and the original v1.

## 4. Motion: what moves and why

Every animation explains a change. Nothing moves on its own except the hero's one-time entrance.

| What moves                            | Why                                                    | How                                                        |
| ------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------- |
| Logo mark, landing → login            | Same brand, same object: it glides instead of blinking | Shared `<ViewTransition name="brand-mark">`                |
| Dashboard nav highlight               | Shows where you went from where you were               | Shared name; it unmounts from one link, mounts in the next |
| Bookings tab underline                | Same, within one page                                  | Shared name                                                |
| Page content                          | Old page leaves fast (120ms), new rises in (220ms)     | `<PageTransition>` in each page (layouts never enter/exit) |
| Skeleton → real content               | A hand-over instead of a pop                           | `<Reveal>` = Suspense + exit/enter view transitions        |
| Booking steps                         | Forward slides left, back slides right                 | `startTransition` + `addTransitionType("step-forward")`    |
| Hero city switch, day change on bands | The bracket moving _is_ the timezone difference        | CSS transitions on `transform` and `left`/`width`          |
| Buttons, Continue, menus              | Feedback that the press registered                     | `active:scale-[0.98]`, short entrance keyframes            |

- **Why React's `<ViewTransition>` and not an animation library:**
  - It drives the browser's View Transitions API, so the browser does the snapshotting and animating.
  - No JavaScript animation loop, nothing new in the bundle.
  - Next.js 16 with React 19.3 supports it with no configuration.
  - Browsers without support simply don't animate.
- **Headers stay put:** both headers have their own `view-transition-name` with the animation switched off, so
  the content moves under a fixed reference point.
- **Clicks during a transition still work:** `::view-transition { pointer-events: none; }`.
- **Reduced motion:** one CSS rule turns every view-transition and keyframe animation to zero. The content
  still changes, it just doesn't move.

## 6. Likely interview questions

- **"How do page transitions work in your app?"** React's `<ViewTransition>` on the browser's View Transitions
  API. Navigations in Next.js are React transitions, so wrapped elements animate automatically. Shared names
  morph one element into another; transition types (`step-forward`) pick the direction.
- **"Why is your mobile menu not a modal?"** It's a disclosure: it pushes content down and doesn't cover the
  page, so there's nothing to trap focus in. A modal would need a focus trap, scroll lock and an inert
  background.
- **"Why Radix for the account menu?"** Menus have a detailed keyboard and ARIA pattern (roles, roving focus,
  typeahead, Escape, focus return). That's a solved problem, and getting it subtly wrong hurts keyboard and
  screen-reader users.
- **"How does your link preview work?"** File conventions: `opengraph-image.png` next to the root layout becomes
  `og:image` with width, height and alt. `metadataBase` makes the URL absolute.

## 7. Stories (problems hit and how they were solved)

### A string constant from a client file broke the build

- **What happened:** the production build failed while prerendering `/` with
  `a.href.startsWith is not a function`.
- **Why:** the footer (a server component) imported `REPO_URL` from the header, which is a `"use client"` file.
  Everything a client file exports reaches the server as a _client reference_, even a plain string. So the
  footer got a reference object instead of the URL.
- **What I did:** moved shared constants to `lib/site.ts`, a plain module both sides can import.
- **Lesson:** the same rule as Day 6's `cityName` story, for data this time. If something isn't a component or
  a hook that needs the browser, it doesn't belong in a `"use client"` file.

### `new Date()` in the footer stopped the page from being static

- **What happened:** the build stopped with "encountered the unstable value `new Date()` while prerendering",
  from the footer's copyright year.
- **Why:** with Cache Components, a static page can't read the clock. On a static page the year would also be
  frozen at build time, so it would be wrong next January anyway.
- **What I did:** removed the year. The footer now says who made it and where.
- **Lesson:** anything time-based on a static page needs a deliberate choice: render it in the browser, or don't
  show it.

### The "live booking page" button disappeared

- **What happened:** after rebuilding, the landing page lost its "See a live booking page" button, even though
  the server was started with `DEMO_BOOKING_PATH`.
- **Why:** the landing page is static, so environment variables are read **at build time** and baked into the
  HTML. Setting the variable only when starting the server changes nothing.
- **What I did:** set it at build time.
- **Lesson:** for deploy day, Vercel's environment variables must be in place **before** the build.

### Brackets that wouldn't slide

- **What happened:** switching cities in the hero, the colours slid smoothly but the white brackets jumped.
- **Why:** each bracket was keyed by its position (`key={left-width}`). A new position meant a new key, so React
  replaced the element instead of updating it, and a CSS transition can't animate an element that didn't exist
  a moment ago.
- **What I did:** keyed brackets by their index in the list, so the same element gets a new `left` and the
  transition animates it.
- **Lesson:** keys decide identity. For an animation, "the same thing moved" and "a different thing appeared"
  are different keys.

### The login bands vanished into the navy panel

- **What happened:** on the navy login panel, the night parts of the bands merged into the background. The
  bands looked cut off.
- **What I did:** put the bands on a white card inside the panel.
- **Lesson:** the band's colours are fixed in meaning, so the band needs a light surface. That's the Day 6
  dark-mode lesson again.

### A missing page returns 200 when it's a username

- **Finding (not fixed yet):** `/a/b/c` returns a 404 status, but `/nobody` returns **200** with the "could not
  be found" page and a `noindex` tag.
- **Why:** `/nobody` matches the `[username]` route. The page starts streaming (and sends its status line)
  before the username lookup inside `<Suspense>` finishes. `notFound()` then can only swap the content and add
  `noindex`; the status is already sent. Search engines respect `noindex`, so nothing gets indexed.
- **Plan:** decide on deploy day whether profile pages should check the username before streaming.
- **Lesson:** with streaming, the status code is decided early. Anything that should change it has to happen
  before the first byte.
