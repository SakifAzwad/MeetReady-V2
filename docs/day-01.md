What was built, and the reasoning to defend each choice in an interview.

**Result:** 54 tests (44 slot logic + 10 database), typecheck, lint, format and production build all green.
Mutation-checked: deliberately breaking the overlap check, the window merge, the DST handling or the
exclusion constraint makes tests fail, so the tests actually guard the behaviour.

## 2. Schema

### Times: the core rule

- **Instants** (when a booking happens) → `timestamptz`. Postgres stores UTC; the driver gives back JS `Date`s.
- **Wall-clock rules** (Mondays 09:00–17:00) → `time` + the host's IANA timezone (`user.time_zone`).

Why not convert availability to UTC when saving? Because "09:00 in New York" is 14:00 UTC in winter and
13:00 UTC in summer. A rule saved as UTC drifts by an hour twice a year. You store what the human meant
(local 09:00 in a named zone) and convert per date. v1 stored `"10:00 AM"` strings with no zone at all.

### Tables

- **user / session / account / verification**: Better Auth's core schema, plus `username` (public URL) and
  `time_zone`. Text ids because Better Auth generates them.
- **event_types**: duration, optional slot interval, location, buffers, minimum notice, booking window,
  max per day. `UNIQUE(user_id, slug)`: slugs only need to be unique per host (`/sakif/intro-call` and
  `/alex/intro-call` can both exist). `is_active` is a soft delete, so past bookings never lose their event type
  (`ON DELETE RESTRICT` on bookings enforces this).
- **availability_rules**: one row per (weekday, start, end). Several rows per day = split hours (lunch break).
  One schedule per host for now; a `schedules` table can be added later without touching `generateSlots`.
- **date_overrides**: replace a date's weekly rules. Both times null = day off. Several rows = several windows.
- **bookings**: `host_id` is copied from the event type on purpose (see below). Status is
  `confirmed | cancelled`; cancelled rows are kept for history and analytics.

### Constraints live in the database, not only in Zod

CHECKs for durations, buffers, slug format, colour, time order, override shape. Zod will give friendly form
errors, but the database is the last line of defence against a bug, a seed script, or (later) an AI tool
writing bad data. The AI guardrail "never let the model write without a tool" pairs with this: even the
tools can't bypass the constraints.

### Double-booking protection: `EXCLUDE USING gist`

```sql
EXCLUDE USING gist (host_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)
WHERE (status = 'confirmed')
```

Read it as: "no two rows where `host_id` is equal AND the time ranges overlap, among confirmed bookings".

- **Why not check in app code?** "SELECT overlapping; if none, INSERT" is a race. Two guests click Book at
  the same moment, both SELECTs see a free slot, both INSERTs succeed. The constraint is checked inside
  Postgres at write time, so exactly one insert wins; the other gets SQLSTATE `23P01`, which the booking
  action will turn into "that slot was just taken".
- **Why not a unique index on (host_id, starts_at)?** It only catches identical start times. A 10:00–11:00
  and a 10:30–11:00 booking would both get in. Overlap is a range question, so it needs a range operator (`&&`).
- **Why `btree_gist`?** GiST indexes handle ranges; the extension lets the same index also handle plain
  equality on `host_id`.
- **Why `host_id` on bookings?** A constraint can only see its own row's columns, not joined tables.
- **Why `'[)'`?** Half-open: 10:00–10:30 and 10:30–11:00 touch but don't overlap. The TS code uses the
  same convention, so the database and the slot generator agree on what "overlap" means.
- **Why `WHERE status = 'confirmed'`?** Cancelling frees the slot. Tested: re-confirming a cancelled
  booking whose slot was taken is also rejected.
- **What it does NOT cover:** buffers and max-per-day. Buffers are a preference ("I'd like 15 minutes
  between calls"), and each event type has different ones, so they're enforced by slot generation and
  re-checked in the booking transaction. The constraint protects the one hard invariant: a host is never
  in two meetings at once.
- **Drizzle can't express EXCLUDE**, so it's a custom migration (`drizzle-kit generate --custom`). The test
  suite runs the real migrations on PGlite (Postgres compiled to WASM, in-process, no Docker), so the
  constraint is proven, not assumed.

### Driver: Neon serverless over WebSockets

`neon-http` is faster for single queries but has no interactive transactions. Booking needs "count today's
bookings, then insert" atomically, so we use the WebSocket `Pool`.

## 3. `generateSlots()`

### Pure function

Inputs: date range, `now`, host timezone + rules + overrides, event type settings, busy intervals.
Output: `{ start, end }[]` as UTC `Date`s. No database, no `new Date()` inside, no network.

Why: it's the most bug-prone logic in the app, and purity makes it trivial to test exhaustively. `now` is
injected so tests can say "pretend it's Monday 09:10" instead of mocking the clock. The same function will
serve the booking page, the booking action (re-check the chosen slot is still valid), the AI
`getAvailableSlots` tool and the MCP server. One implementation, one set of tests.

### Algorithm

1. List host-calendar dates covering the range, plus one day before (catches a window running past midnight
   into the range).
2. For each date: overrides if any exist for it, else the weekly rules for that weekday. Convert each
   window to UTC instants **for that specific date**.
3. Merge overlapping/touching windows. Fixes duplicate slots from overlapping rules and lets a
   22:00–24:00 + 00:00–02:00 schedule produce a slot spanning midnight.
4. Step through each window by `slotInterval` (default: duration). Keep a candidate if it fits the window,
   is in the range, is ≥ `now + minimumNotice`, its host date is within the booking window, its day isn't at
   `maxBookingsPerDay`, and it doesn't conflict with busy time.

### DST: the subtle part

- **Construct local times directly**, never "local midnight + 9 hours". On a DST day midnight + 9h is 08:00
  or 10:00 local. (Mutation-tested: switching to midnight+minutes breaks three tests.)
- **Spring-forward gap** (02:00–03:00 doesn't exist): non-existent times move forward. A 02:00–04:00 rule
  becomes 03:00–04:00, so we never offer a slot at a time that doesn't exist.
- **Fall-back overlap** (01:00–02:00 happens twice): ambiguous times take the earlier occurrence.
  A 00:00–03:00 rule is 4 real hours that night, so it produces 4 one-hour slots. Slots are measured in
  real elapsed time; a meeting is 60 real minutes regardless of what the clock says.
- These are the same rules as the upcoming `Temporal` API's "compatible" mode, via `@date-fns/tz`'s `TZDate`.

`@date-fns/tz` rather than `date-fns-tz` (in the original plan): with date-fns v4, `@date-fns/tz` is the
official timezone package by the same team.

### Dates as strings (`DateKey = "YYYY-MM-DD"`)

A `Date` is an instant, and which day it's on depends on the timezone. "Is this the host's Monday?" needs a
plain calendar date, so `DateKey` is a branded string. Day arithmetic is done in UTC, where every day is
24h, so DST can't skew it. ISO date strings also sort correctly as strings.

### Buffers: gap = max, not sum

A slot conflicts if (slot + its buffers) overlaps a meeting, OR the slot overlaps (meeting + that meeting's
buffers). Buffers are free time around meetings, so two buffers may share the same free time: a 15-min
"after" buffer and a 15-min "before" buffer need a 15-minute gap, not 30. (Tested.)

### Limits

- **Minimum notice:** instant-based (`now + N minutes`).
- **Booking window:** by host calendar day (today … today + N − 1). Instant-based would make the last day's
  afternoon slots appear and vanish depending on the current time of day.
- **Max per day:** counted by the host's local date, using only busy items flagged
  `countsTowardDailyLimit` (bookings of this event type). Other events still block their time but don't
  count. Tested with a booking that's Monday in UTC but Tuesday in Dhaka.

### Viewer timezone is a display concern

`generateSlots` never sees the guest's timezone. It returns instants; `groupSlotsByDate(slots, guestTz)`
puts them under the guest's own dates. A London host's Monday 18:00 shows under Tuesday for a guest in Tokyo.

### Complexity

O(slots × busy). For a month of 30-min slots and a few dozen bookings that's a few thousand comparisons,
well under a millisecond. If it ever mattered, sort busy intervals and sweep with two pointers: O(n + m).

## 4. Tests

- **Example tests (39, incl. interval and time helpers):** each rule, each DST case, overrides, buffers, limits, validation, grouping.
- **Property-based tests (5, fast-check):** hundreds of random hosts across 6 timezones (including
  Lord Howe's 30-minute DST shift and Kathmandu's +05:45), random rules, bookings, buffers and limits over
  March 2026 (both US and UK DST changes). Invariants: every slot is exactly the duration; no slot overlaps a
  booking; strictly increasing; inside the range and after the notice period; no rules → no slots. On
  failure, fast-check shrinks to the smallest failing input.
- **Database tests (10):** real migrations on PGlite. Overlap rejected (`23P01`), adjacent allowed, other
  host allowed, cancellation frees the slot, re-confirm blocked, CHECKs and unique slug enforced.
- **Not yet covered:** truly concurrent inserts (PGlite is single-connection). That test comes with the
  booking action, against a Postgres service container in CI.

## 5. Likely interview questions

- **"How do you prevent double booking?"** Postgres exclusion constraint on `(host_id, tstzrange)` with
  `&&`, partial on confirmed. App-level checks race; the DB check is atomic. Catch `23P01` → friendly error.
- **"Why store availability in local time?"** Because the human's intent is local. UTC rules drift with DST.
- **"What happens at DST changes?"** Gap times shift forward, ambiguous times take the earlier occurrence,
  durations are real elapsed time. Show the three tests.
- **"Why is slot generation pure?"** Testable without mocks, reusable by UI, server action, AI tool and MCP.
- **"How do you know your tests are good?"** Property-based tests for invariants plus mutation checks:
  I broke the code on purpose and confirmed tests fail.
- **"Why denormalize host_id?"** Constraints can't see joins. The cost is keeping it in sync, which happens
  in exactly one place (the booking insert).
- **"Why Drizzle over Prisma?"** SQL-shaped API, schema in TS with no separate DSL or codegen step, thin
  runtime that suits serverless, and easy escape to raw SQL (needed here for EXCLUDE).

## 6. Stories (problems hit and how they were solved)

Interviewers ask "tell me about a bug you fixed" or "a decision you made". Each story: what happened → what I
did → what I learned.

### "Works on my machine": CI failed on typecheck

- **What happened:** `npm run typecheck` passed locally, but failed in GitHub Actions with
  `Cannot find name 'LayoutProps'`.
- **Why:** `LayoutProps` is a type Next.js generates into `.next/` when you run `dev` or `build`. My machine
  had a `.next` folder; CI starts from a fresh clone, so the type didn't exist.
- **What I did:** reproduced it by deleting `.next` locally, then changed the script to
  `next typegen && tsc --noEmit` so types are generated first. Verified from a clean state.
- **Lesson:** CI is a clean environment on purpose. When something passes locally and fails in CI, look for
  state that only exists on your machine (generated files, caches, env vars).

### Proving the tests can actually fail

- **Question:** 44 tests passed first time. Are they testing anything?
- **What I did:** planted bugs on purpose (mutation testing): removed the busy-time check, removed the window
  merge, and swapped DST-correct time building for "midnight + N minutes". Each bug failed 3–7 tests. Then I
  replaced the exclusion-constraint migration with `SELECT 1`: 3 database tests failed.
- **Lesson:** a green test suite only means something if you've seen it go red for the right reason.

### Dependency conflict: not forcing past it

- **What happened:** installing Vitest 5 failed with a peer-dependency error: it needs `@types/node` 22+,
  the starter template had 20.
- **What I did:** upgraded `@types/node` to 22 to match the Node 22 runtime, instead of
  `--legacy-peer-deps`.
- **Lesson:** a peer conflict is usually telling you something real. Here the types were simply wrong for the
  Node version we run.

### Build depended on the internet

- **What happened:** `next build` failed in a network-restricted environment: `next/font/google` downloads
  fonts from Google at build time.
- **What I did:** switched to the `geist` npm package, which ships the font files in `node_modules`.
- **Lesson:** builds should be reproducible without outside services. Fewer things that can break a deploy.

### Catching a naming problem before it was deployed

- **What happened:** the generated migration named a constraint `event_types_userId_slug_unique`
  (camelCase inside a snake_case database).
- **What I did:** named it explicitly and regenerated the migrations from scratch.
- **Lesson:** migrations are free to rewrite before they've run anywhere real; after deploy, every change
  needs a new migration. Review generated SQL before the first deploy.

### Choosing the database region

- **Decision:** Neon in AWS US East 1, even though I develop from Bangladesh.
- **Why:** the database should be close to the **server**, not the developer or the user. Vercel functions
  run in Washington DC by default, and one page can make several queries, each a round trip. Recruiters
  (the real users of the demo) are mostly in the US/EU too.
- **Trade-off accepted:** ~250 ms per query in local development.
- I also skipped `neon init` and the extra Neon services (hosted auth, storage, realtime): every part of the
  stack stays code in the repo that I can explain.
